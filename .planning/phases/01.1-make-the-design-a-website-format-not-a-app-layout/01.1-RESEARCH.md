# Phase 01.1: Website Layout Correction - Research

**Date:** 2026-05-02
**Status:** Complete

## Research Question

What do we need to know to plan a fast correction from an app-style mobile card layout to a website-format presentation, while preserving the Phase 1 Next.js scaffold and January 1, 2016 default-state wiring?

## Key Findings

### Existing codebase starting point

- The current home page already has useful pieces:
  - a normalized default weather record
  - a reusable app shell component
  - a dedicated scene shell boundary
- The main mismatch is presentation structure, not data or routing.
- This means the correction phase should be a refactor of composition and layout primitives, not a rebuild of the weather domain layer.

### Website-format implications

- The current shell centers a mobile-sized card in a full-screen background, which reads as an app mockup rather than a website.
- A website-format correction should:
  - remove the fake mobile device framing
  - give the page a real desktop composition with a full-width or content-width layout
  - preserve a strong hero/scene region so later 3D work still lands naturally
- The website should still feel visually directed by `weather.jpeg`, but as a webpage rather than a phone screenshot reproduction.

### Structural recommendations

- Keep the route and data loading model intact.
- Split layout responsibilities into clearer website sections:
  - page wrapper/background
  - hero copy/date block
  - scene section
  - metrics/timeline support region
- Preserve the scene shell component boundary so Phase 3 can upgrade the visual system in place.

### Validation implications

- The safest verification is a mix of:
  - build + typecheck
  - render assertions proving the page still shows the January 2016 state
  - human visual confirmation that the page reads as a website instead of a mobile app mockup

## Recommendations

1. Refactor the main shell layout first, not the scene implementation.
2. Replace the mobile-card container with a desktop-ready website wrapper and content grid.
3. Keep `app/page.tsx` and the normalized weather-record load path stable.
4. Update tests to assert the website shell structure rather than the previous card framing.

## Validation Architecture

- Use the existing Vitest + Testing Library stack from Phase 1.
- Keep automated checks focused on:
  - successful render of the updated page shell
  - continued visibility of the January 2016 default state
  - preservation of the scene shell and metrics region
- Use manual visual review to judge whether the result reads as a website.
